# 项目复盘

## 项目完成情况

实际个人投入约 3–4 小时。

已完成真实模型驱动的取证循环、检索与原文读取、引用校验、冲突处理、上下文追问、失败与执行上限处理，以及 CLI、离线 Mock 和配套验收材料。具体结果见 [评估文档](03-evaluation.md)。

## 关键问题与方案取舍

本项目最难的问题是确定查证的停止条件。检索到“30 天”和“15 天”两条原文，仍可能无法确定适用期限；而用户仅询问某条规则是否适用时，原文已明确排除其情况，就足以回答当前问题。停止判断需要同时考虑用户诉求、原文支持程度和未解决的冲突，不能仅以是否找到资料或是否调用过工具为依据。

开发中曾出现最终回复保留了冲突，但取证阶段仍将证据标为充分的情况。为此，项目明确区分证据状态与最终任务状态：冲突未经消解时，取证阶段记录 `conflict`；回复阶段再根据用户是否能够补充线索，决定追问或说明无法确定。测试也补充了取证原因检查，并保留对查证动作和最终答复的检查。相关场景的实际结果见 [评估文档](03-evaluation.md#3-两阶段状态与动态决策验证)。

方案上采用独立的取证循环与回复模块，由程序直接传递原文，便于分别约束证据判断、引用选择和答案表达。阶段拆分仍需配合一致的提示词、状态定义和验证规则；它也增加了模型调用与原文交接开销，因此两个阶段共用执行预算，回复阶段最多发起一次补查。

## 实践总结

- **证据充分性需要结合具体问题判断。** 原文存在、引用准确只是基础，还要检查适用条件、起算点及冲突关系。将这些要求落实到取证结束条件和回复规则中，才能减少过早作答与无必要的补查。
- **验证需要同时检查结果和过程。** 固定措辞断言可能将合理表达判为失败，只检查最终答案又可能漏掉错误的证据判断。结构化字段、引用来源和工具执行适合自动检查；结论是否得到原文支持、查证是否围绕用户诉求展开，需要结合输入、原文和 Trace 阅读核对。
- **连续对话需要保留可核验的原文依据。** 历史回答能够帮助理解指代，但不能替代制度原文。追问中的引用缺失问题说明，会话除了保留对话文本，还需要管理证据来源和有效性；资料变化后，应让旧证据失效并重新查证。

## 现存不足

- 部分回复仍包含多余背景或不够精确的措辞，答案、缺口和追问之间也有进一步精简的空间。
- 验证基于小型合成资料与固定用例，尚不足以说明在更大资料集、更多问题表达和复杂制度关系下的表现。

## 后续改进与验证计划

| 改进方向 | 计划措施 | 验证方式 |
| --- | --- | --- |
| 回答表达 | 精简回复约束，减少重复背景、缺口说明与追问 | 对比相同输入下修改前后的回答，检查冗余是否减少，同时保留必要条件、有效引用和正确状态 |
| 场景覆盖 | 扩充相似条款、适用范围、冲突关系和多轮条件更正用例 | 为新增用例明确预期结论与原文依据，核对回答和查证路径，并回归既有必验场景 |
| 检索优化 | 比较 BM25、向量与混合检索，并探索引入 reranker 重排 | 在相同资料与问题上检查支持条款、冲突双方的召回及排序，比较任务结果、耗时与调用开销 |
| 知识组织方案调研 | 调研 LLM Wiki 等知识组织方式，评估是否适合本项目 | 选取代表性制度场景构建小规模对照，比较原文追溯、更新维护和问答效果 |

以上为后续优化与调研计划，不属于本次实现范围，也不计入当前验证结果。
