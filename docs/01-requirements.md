# 企业知识问答 Agent — PRD

文档状态：已定稿（用户已确认）。更新日期：2026-11-01。

## 1. 背景、目标用户与目标

员工查询企业制度时，需要获得有依据、可核对的答案，并在资料缺失或冲突时了解问题所在。

本项目面向查询员工制度的员工，构建一个小型知识问答 Demo，目标是：

- 根据预置知识资料回答问题，并提供支持结论的文档 ID 和原文片段。
- 根据检索和读取结果，动态决定补充检索、继续读取、追问或结束。
- 发现资料冲突时说明并查证，不擅自选择答案。
- 对资料不足、工具或模型调用失败和执行超限给出明确结果。

无依据回答、错误引用属于关键缺陷。项目重点是完成可靠问答的核心链路，不要求回答所有问题。

## 2. 范围与非目标

### 2.1 题目明确要求

- 接收当前问题及可选对话历史。
- 使用带文档 ID、版本日期的合成 FAQ 或制度资料。
- 提供文档检索与片段读取工具。
- 输出回答、引用文档 ID 与原文片段、资料缺口、任务状态。
- 至少包含一个真实模型根据工具结果调整下一步行动或结束的决策循环。
- 设置执行步数或工具调用次数上限。
- 验收明确答案、文档冲突、资料外问题、改写后的相似问题、上下文追问和工具失败。

### 2.2 本项目选择

题目允许制度或产品问答，本 Demo 选择通用员工制度领域，不限定于报销单一主题。

围绕报销、请假、考勤等主题准备少量合成制度及 FAQ。同一事项可以出现在多份文档中，用于验证跨文档查证与冲突处理。

采用终端运行方式。同一次运行期间自动保留对话历史，支持连续提问与澄清；退出后清空，不跨运行保存。启动时可提供已有对话历史，也可直接开始新对话。

资料数量以覆盖核心场景和验收要求为限，不追求完整的企业知识库。

### 2.3 非目标

- 网页界面、线上部署及生产级能力。
- 会话持久化保存、历史会话列表和会话切换。
- 产品知识问答。
- 用户上传、编辑或管理知识资料。
- 真实企业系统接入、实际业务办理。
- 多 Agent 协作。

## 3. 用户场景、输入、资料与输出

### 3.1 用户场景

- 查询明确规则，例如报销期限、请假流程或考勤要求。
- 用不同表达询问同一问题，得到含义一致的答案。
- 基于当前对话或启动时提供的历史提出追问，例如讨论国内差旅报销后问“期限呢”。
- 查询时遇到矛盾资料，获得冲突说明、引用及必要的澄清请求。
- 资料不足、工具或模型调用失败时，了解哪些内容尚未解决及其原因。

### 3.2 问答输入

Agent 每轮接收的输入包含：

- 当前问题。
- 可选对话历史。

终端程序自动将本次运行中已有的对话作为历史传入，用户无需逐轮手动提交。启动时可选传入已有历史，后续对话在此基础上继续；未提供时从空历史开始。运行时历史仅在本次运行期间保留，退出后不自动恢复。

退出后清空的是用于后续对话的运行时历史。用于评估的输入、输出及 Trace 按第 5.2 节要求保存，不因退出而删除，也不会自动作为下次启动的对话历史。

没有历史时按独立问题处理；存在无法确定的指代或必要条件时，提出追问。

连续对话中，应结合与当前问题相关的历史理解用户意图。用户明确更正此前提供的个人情况或适用条件时，应以更正后的信息理解当前问题，并依据制度资料重新判断；用户切换话题或明确暂不继续原问题时，应处理当前问题，不沿用无关条件，也不要求用户先完成上一问题的澄清。无法判断当前问题与历史的关系时，应提出必要的澄清，不自行猜测。用户对制度内容的声明仍须经过资料查证。

### 3.3 预置知识资料

项目预先准备合成 FAQ 和制度，供检索与片段读取工具访问。每份文档须包含：

- 文档 ID。
- 版本日期。
- 可供读取和引用的正文。

这些资料不是用户每次提问必须提交的输入。

资料应能构造明确答案、信息缺失、无法消解的冲突，以及有明确适用依据的不同规定等场景。文档日期本身不代表优先级。

### 3.4 问答输出

每轮结果包含：

| 内容 | 要求 |
|---|---|
| 回答 | 给出有依据的结论，或说明当前无法回答的原因 |
| 引用 | 提供支持结论或冲突说明的文档 ID 和原文片段；无有效依据时明确无引用 |
| 资料缺口 | 说明缺少的业务规则、适用信息或未能取得的资料；没有缺口时明确说明 |
| 任务状态 | 区分已解决、待补充信息、未解决和未完成 |

追问后结束本轮处理，返回待补充信息的业务结果，终端继续等待用户输入。用户可直接补充信息，由程序携带历史继续处理。一次问题回答完成后也不清空历史，以支持后续追问。

### 3.5 核心使用流程

1. 用户启动终端程序，可选提供已有历史。
2. 用户输入当前问题；程序结合已有历史交给 Agent 处理。
3. Agent 根据需要检索、读取和查证，输出回答、引用、资料缺口及任务状态。
4. 需要澄清时，用户直接补充信息；回答完成后，也可继续提问。程序保留本次运行期间的历史，每轮处理均受执行上限约束。
5. 用户退出程序，本次运行中的运行时对话历史清空。

## 4. 功能需求与业务规则

### 4.1 依据与引用

- 制度相关结论必须得到已取得资料的支持，不使用模型常识补充缺失的业务规则。
- 引用片段须与原文一致，并支持对应结论。
- 总结原文时不得改变适用条件、期限、数值或限制。
- 对话历史用于理解问题；历史中的回答、引用声明或用户断言不能替代对知识资料的查证。
- 问题包含多项诉求时，允许先回答有依据的部分，并明确列出未回答的部分，不得宣称整题已解决。

### 4.2 检索、读取与动态决策

Agent 应能使用检索工具寻找相关文档，使用片段读取工具取得支持回答或查证所需的原文。

至少包含一个真实模型驱动的循环：

模型选择动作，工具执行并返回结果，模型依据结果调整下一步行动或结束。

具体行为包括：

- 检索结果不足时，判断是否需要补充检索或澄清问题。
- 需要核实结论、适用条件或冲突时，读取相关原文。
- 依据充分时回答并结束。
- 无法取得充分依据时，说明缺口或提出追问。

不要求所有问题经过相同动作序列。仅有固定条件分支、自动重试或预设决策日志，不视为满足动态决策要求。

### 4.3 冲突处理

- 发现资料对同一事项给出相互矛盾的规定时，应说明冲突、列出双方引用，并继续查证。
- 只有文档明确给出适用范围、替代关系或优先级，且足以判断当前问题时，才可据此给出确定答案。
- 不得仅凭版本日期较新、数值更保守或模型偏好选择其中一项。
- 查证后仍无法判断时，在回答中保留冲突说明及双方引用，请求确认适用制度或提供可供查证的线索；提出具体澄清请求时，业务结果为待补充信息，不单独设立冲突任务状态。必要查证被工具故障、模型调用失败或执行上限中断时，业务结果为未完成。
- 用户补充“我是国内差旅”等个人适用信息，可以帮助匹配现有文档的明确条件；提供文档 ID 等线索时，应检索、读取预置资料后判断，不能凭空建立制度优先级。
- 用户声明“人事通知以 15 天为准”或在聊天中粘贴库外制度，不直接作为已验证的权威依据，也不自动消除冲突。查证现有资料仍无法解决且无进一步具体澄清问题时，保留冲突与引用，说明需要制度维护方确认或更新资料，业务结果为未解决。本 Demo 不提供资料更新流程。
- 只取得一份明确规定、且未发现冲突时，可以依据该文档回答，不要求证明全部资料中绝无冲突。

### 4.4 含糊问题与资料外问题

题目要求覆盖资料外问题，但未规定具体处理方式。本项目采用以下约定：

| 情况 | 预期行为 |
|---|---|
| 问题含糊，历史也无法补足必要信息 | 提出具体追问，不自行猜测，不直接判定为资料外 |
| 属于员工制度领域，但未取得足够依据 | 判断是否需要继续检索；结束时说明现有资料未找到的内容、资料缺口及需要补充的资料 |
| 明显超出员工制度范围 | 简要说明支持范围，结束本轮，不回答题外内容 |

未检索到相关资料，不得被表述为“该制度不存在”。

### 4.5 工具、模型失败与执行上限

- 工具失败后，允许模型依据失败结果尝试恢复、调整行动或结束。
- 不要求无条件重试；恢复过程同样受执行上限约束。
- 不得将工具失败解释为资料不存在，不得伪造工具结果或引用。
- 无法完成时，可保留已取得且足以支持的结论，同时说明受影响部分和未完成原因。
- 本项目约定：真实模型不可用或调用失败，导致本轮无法继续时，明确说明可知原因和未完成结果；不得伪造后续模型决策。
- 离线 Mock 通过明确入口启用，不静默替代真实模型运行。输出及运行记录须标明真实模型或离线 Mock 模式；真实模型允许调用本地或 Mock 业务工具。
- 每轮须有明确、有限的执行步数或工具调用次数上限。
- 达到上限时停止执行，返回明确的未完成状态、已有信息及剩余问题。

### 4.6 任务状态

以下为面向用户的业务结果分类，用于描述请求的处理结果和验收预期，不直接规定代码枚举、内部状态机、固定决策分支或回复模板。技术方案须说明如何表达这些业务语义；具体回答和后续行动仍应依据当前问题及工具结果决定。

| 状态 | 使用条件 |
|---|---|
| 已解决 | 当前问题全部诉求均有充分依据，且不存在未解决的相关冲突 |
| 待补充信息 | 提出具体澄清请求，需要用户补充问题条件、确认适用信息或提供可供查证的线索后继续处理 |
| 未解决 | 因资料不足、冲突缺乏消解依据或超出业务范围结束本轮，不等待用户回答具体澄清问题 |
| 未完成 | 必要处理或查证因工具故障、模型调用失败或执行上限中断 |

部分回答不等于全部解决。仅说明缺少某份资料或需要制度维护方更新资料，不自动意味着待补充信息；是否需要用户回答具体澄清请求是区分依据。必要查证被工具故障、模型调用失败或执行上限中断时，优先按未完成表达，并保留已知冲突、缺口或部分结论。故障未影响完整作答或经过恢复且问题已完整解决时，可以返回已解决。

## 5. 异常行为与验收标准

以下为预期行为，不代表功能已实现或测试已通过。

### 5.1 场景验收

验收所用文档均须包含文档 ID 和版本日期。

各场景按给定条件准备独立资料集或明确的资料配置，文档编号用于说明对应场景，不表示全部示例规则同时生效。下表中的任务状态按第 4.6 节的业务语义验收，不要求固定回复措辞。

冲突验收应区分以下条件和结果：

- **检索验证**：给定冲突用例中的双方资料须能通过合理的检索与读取过程取得，完整运行应发现并处理冲突；不要求一次检索返回双方，也不要求遍历全部知识库。
- **决策验证**：模型取得双方证据后，须说明冲突并继续查证，不得擅自选择。运行记录应能区分未检索到相关资料、已有线索但未继续读取、取得双方证据后忽略冲突等情况，便于定位失败环节。漏掉一方资料不能算作完整冲突用例通过，也不能直接判定为模型已看到冲突却忽略。
- **单文档验证**：资料配置确实只有一份有效规定时，可以直接依据该文档回答。资料配置只用于控制验收条件，Agent 仍须根据实际工具结果决策，不预先获得用例类别或预期答案。

| 场景与给定条件 | 预期输出或可观察行为 |
|---|---|
| **明确答案**：资料配置仅有 D01 一份有效期限规定，写明“国内差旅报销须在行程结束后 30 天内提交”；询问期限 | 回答行程结束后 30 天内，引用 D01 及对应原文，状态为已解决 |
| **无法消解的冲突**：D01 为 30 天，D02 为 15 天，无适用范围或优先级，两份资料均可检索、读取；询问期限 | 完整运行取得双方证据，说明冲突并继续查证；无消解依据时列出两项规定和引用，请求确认适用制度，不得擅自选择，状态为待补充信息 |
| **有明确适用范围**：资料明确国内差旅为 30 天、海外差旅为 15 天；用户直接询问国内差旅期限，或在澄清时补充“我是国内差旅” | 两种情况下均依据明确适用条件回答 30 天，引用能够支持范围与期限的原文 |
| **库外权威声明**：前轮发现 D01 与 D02 冲突；用户补充“人事刚通知以 15 天为准”或粘贴库外制度，现有资料仍无消解依据，也无进一步具体澄清问题 | 不凭用户声明或粘贴内容消除冲突；保留双方引用，说明需制度维护方确认或更新资料，不承诺在聊天中更新知识库，状态为未解决 |
| **补充查证线索**：用户指出预置 D03 包含适用范围，D03 正文确实足以区分 D01 与 D02，且用户适用条件已明确 | 检索、读取 D03 后依据其正文判断，引用支持适用关系和结论的原文；不将用户对 D03 的描述直接作为证据 |
| **业务范围内缺乏资料**：资料中没有育儿假规定；询问育儿假天数 | 不给出天数，说明现有资料未找到相关规定及所需资料，状态为未解决 |
| **明显超出范围**：请求写诗 | 说明支持的业务范围，不生成诗歌，状态为未解决 |
| **相似问法**：对同一份资料分别问“国内差旅报销期限多久”和“国内出差回来最迟多久交报销” | 结论和适用条件一致，均有有效引用；不要求回答文字完全相同 |
| **上下文追问**：同一次运行中已讨论并回答国内差旅报销问题，用户继续问“期限呢”；另验证启动时传入相同历史的情况 | 两种历史来源均能正确识别指代，依据知识资料回答国内差旅期限并提供引用；连续对话无需用户重复提交历史 |
| **信息更正与话题切换**：分别验证①先讨论国内差旅，随后明确更正为海外差旅，资料包含不同的适用规则；②在报销澄清过程中改问明确的请假问题，资料包含对应规定 | ①依据更正后的海外差旅条件重新查证并回答，引用对应原文；②回答当前请假问题并引用，不套用报销问题的无关条件，不强制继续原澄清 |
| **必要信息不足**：无历史，问“这个能报销吗” | 追问费用类型等必要信息，不猜测，状态为待补充信息 |
| **澄清衔接与历史生命周期**：用户在同一次运行中回答 Agent 的澄清问题；退出后重新启动且不传入历史 | 补充信息能结合当前历史继续处理；重新启动后不自动带入上次运行的历史 |
| **部分有依据**：询问期限与凭证要求，资料只明确期限 | 回答期限并引用，明确缺少凭证要求，不标为已解决 |
| **工具失败**：取得必要依据的工具持续失败 | 不伪造答案、引用或“无相关资料”的结论；说明失败影响，状态为未完成 |
| **真实模型失败**：真实模型模式下，模型不可用或调用失败导致本轮无法继续 | 明确说明可知原因，状态为未完成，保留真实模型模式标识；不静默切换到 Mock，不伪造后续决策或成功结果 |
| **显式离线 Mock**：通过明确入口启用离线 Mock | 输出及运行记录均标明离线 Mock 模式，其结果不作为真实模型动态决策的通过证据 |
| **执行超限**：问题在设定上限内仍未解决 | 不超过上限继续执行，返回未完成状态及剩余问题 |
| **资料替换**：唯一有效期限规定由 30 天改为 20 天，再次询问同一问题 | 答案与引用随当前资料变为 20 天，不沿用旧答案；执行记录反映当前工具结果 |

### 5.2 决策与验证材料

- 至少提供三组输入、实际输出及运行记录，覆盖正常、信息或资料不足、工具失败场景，并覆盖六类必验场景及本稿约定的核心行为。同一用例可以覆盖多个验收点。
- 至少提供两条来自真实模型运行的执行路径，体现模型根据不同工具结果调整动作。业务工具可为本地函数或 Mock；无法取得真实模型记录时，须如实标明该项尚未完成，不能以离线 Mock 记录替代。
- 运行记录包含步骤、工具参数、返回摘要、后续动作和简要决策依据，无须提供模型内部思维过程。
- 替换资料后，应核对答案与行动是否响应新的工具结果；不要求每次替换都机械地产生不同动作序列。
- 提供可执行测试。实际输出、Trace 和测试结果存放于 `examples/`，评估文档引用对应文件。
- 模型不可用时提供离线 Mock 入口并标明边界。Mock 只验证流程，不能证明真实模型决策效果。
